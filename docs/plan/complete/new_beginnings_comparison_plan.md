# new-beginnings 대비 기능 격차 분석 및 개선 계획

> 작성일: 2026-07-24 (2026-07-24 1차 수정 — §1·§2 원인 분석 정정)
> 배경: 사용자가 `c:\ai\new-beginnings`(자매 프로젝트)와 비교했을 때 ClearSurvey의 UI·기능이
> 부족하다고 느낌 — 구체적으로 ① 파일 형식(xlsx만 지원, csv/json 미지원) ② 테마 색상 정확도
> (특히 토스 차트에 주황계열이 섞여 나오는 것)를 지적함. 두 프로젝트 소스를 직접 대조해 실측한
> 결과를 정리한다.
> 상태: **분석 완료 — 실행 여부/우선순위는 결정 대기**
>
> **1차 수정 경위**: 최초 작성본에서 ① CSV/JSON 미지원 원인을 "정제 파이프라인이 엑셀 전용
> API에 구조적으로 결합"이라고 썼으나, 사용자가 "포맷별 로더 3개 + 공통 DataFrame 변환"
> 구조를 제안하며 반문 → `backend/engine/pipeline.py`를 다시 읽어보니 **그 구조가 이미
> 존재했다**(`_sheet_to_dataframe()`가 유일한 변환 지점이고 그 이후 전부 포맷 무관). 최초 분석이
> 틀렸으므로 §1을 정정했다. ② 토스 차트의 주황색 원인도 처음엔 "자동 합성 필러 색"이라고
> 추정했으나, 실제로는 `theme/overrides/toss.json`에 **의도적으로 기록된 값**임을 확인해 §2를
> 정정했다.
>
> **3차 후속 수정 — 리커트 척도 오분류**: §4-B(CSV/JSON) 작업 직후, 사용자가 "1~5점 선택 응답이
> 자동으로 숫자로 바뀌어 합계로 나오는지, 원래는 1점 몇 명·2점 몇 명으로 나와야 한다"고 질문함.
> 확인 결과 도넛/바 차트 자체는 `aggregate.ts`의 `aggCategory()`가 값을 문자열화해 카운트하므로
> 안전했으나, **새 프로젝트 생성 시 자동 제안되는 기본 KPI**(`exporter.py`의
> `_build_default_dashboard`)가 값이 전부 정수인 컬럼을 무조건 `numeric`으로 분류해 "OO 합계"
> 카드를 만드는 문제를 발견함(엑셀은 "텍스트 서식"으로 이를 피할 수 있었지만 CSV/JSON은 그
> 회피 수단이 없어 이번에 새로 노출됨). `_detect_type()`에 `_looks_like_rating_scale()` 판별을
> 추가해 리커트(1~5·1~7)·NPS(0~10)류 정수 컬럼을 `category`로 재분류하도록 수정(§4-D).
>
> **2차 수정 경위 — 실제 적용**: §2의 처방을 실행에 옮기면서 처음엔 `overrides/toss.json`의
> 값 5개를 손으로 다른 hex로 바꾸는 방식으로 적용했다. 사용자가 "임의로 값을 수정하는 방식이
> 아니라 `design_system_guides`의 원형을 받아 변환로직(메인/서브/강조1/강조2)에 따라 대입하는
> 형식이어야 한다"고 재차 정정 → override 파일이 아니라 **`build-themes.mjs`의 차트 자동
> 도출 함수(`draftPalette()`) 자체의 후보 우선순위를 고쳐서**, 원형 문서에 실제 정의된 값만으로
> 토스 차트가 재도출되도록 했다(§2-D). `overrides/toss.json`은 더 이상 필요 없어져 삭제했다.
> 코드 변경까지 반영 완료, 테스트(테마 135개 + 전체 481개) 통과 확인.

## 0. 결론 요약 (TL;DR)

| 지적 사항 | 실측 결과 | 원인 | 이식 가능성 |
|---|---|---|---|
| CSV/JSON 미지원 | **사실** — 서버(`main.py`)가 `.xlsx`만 허용, 프론트도 `.xlsx`만 accept | **업로드 게이트 한 줄 + 포맷별 로더 부재일 뿐, 파이프라인 자체는 이미 포맷 무관 구조**(§1 정정) — `_sheet_to_dataframe()` 하나만 통과하면 그 뒤는 pandas DataFrame으로 전부 동일 | **매우 높음** — 최초 평가(구조적 결합)는 과장이었음. CSV 로더 신설은 중~소 규모 작업 |
| 토스 차트에 주황이 섞임 | **버그도 자동생성 사고도 아님** — `theme/overrides/toss.json`에 **의도적으로 기록된 값**(§2 정정). 다만 실제 토스 제품/브랜드 정체성과는 어긋나는 **큐레이션 판단**일 가능성 높음 | 차트 5색의 "구분 가능성"을 우선시하는 원칙(`theme_system_plan.md` §2-D)에 따라 토스의 semantic 색(success 초록·warning 주황)을 categorical 차트색으로 재사용함. new-beginnings는 primary 색상 스케일(50~900 10단계)이 있어 "파랑 계열 단색 그러데이션" 차트가 가능하지만 clearsurvey는 그 스케일 자체가 CSS에 없음(§2 구조적 차이) | **매우 높음** — `overrides/toss.json` 1개 파일, 배열 값 5개만 바꾸면 즉시 반영 |

이 문서가 확인한 가장 중요한 사실: **두 프로젝트는 독립적인 경쟁 구현이 아니라 같은 디자인
시스템 자산(`design_system_guides/`, 테마 카탈로그 생성 스크립트)을 공유하는 자매 프로젝트다.**
`clearsurvey/frontend/src/theme/registry.gen.ts`에는 `ink`/`forest` 테마 출처가
`"new-beginnings/public/data/themes.json (수작업 이관)"`이라고 명시돼 있고, `toss` 슬러그 충돌 시
"new-beginnings도 카탈로그가 레거시를 덮는 순서"라는 비교까지 이미 기록돼 있다. 따라서 아래 격차는
"새로 만들어야 하는 기능"이 아니라 대부분 **"이미 있는 걸 더 꺼내 쓰는" 작업**이다.

## 1. 파일 형식 지원 (xlsx vs csv/json/xlsx)

### 1-A. 무엇이 다른가 (표면)

| | clearsurvey | new-beginnings |
|---|---|---|
| 서버 업로드 게이트 | `backend/app/main.py:407` `if not safe_fname.lower().endswith(".xlsx")` → 그 외 전부 거부 | 없음(서버 게이트 자체가 없음, 아래 참조) |
| 프론트 업로드 UI | `Step1_ProjectUpload.tsx` — `accept=".xlsx"`, `.xls`도 토스트로 거부 | `upload-local.tsx` — `accept=".csv,.json,.xlsx,.xls"` |
| 결과 데이터 소스 | `storage/raw/` → 백엔드 정제 파이프라인 → `frontend/public/data/{name}_data.json` (서버가 정제한 값) | `/data/local-upload.json`에 즉시 반영 — **정제 파이프라인 없이 원본 그대로 미리보기** |

### 1-B. 왜 다른가 — **정정: 구조적 결합이 아니었다**

> [!WARNING]
> 최초 작성본은 "정제 파이프라인이 openpyxl(엑셀 전용 API)에 구조적으로 결합돼 있다"고 썼다.
> **틀렸다.** `backend/engine/pipeline.py`를 다시 확인한 결과, 사용자가 제안한 구조
> ("포맷별 로더로 DataFrame을 만들고, 그 뒤 변환 과정은 공통으로 쓴다")가 **이미 그대로
> 구현돼 있었다.**

실제 구조는 3단이 이미 맞다:

```
① 포맷별 로더            ② 포맷 무관 파이프라인              ③ 내보내기
openpyxl 워크북      →   pandas DataFrame  →  clean_value/     →  {name}_data.json
(엑셀 전용)               (0-based 컬럼,        transform/       (완전 포맷 무관,
                          원본 행번호 index)     overrides 등       기존 그대로)
```

- 변환 지점은 `pipeline.py:24` **`_sheet_to_dataframe(wb, cfg) -> pd.DataFrame`** 딱 하나다.
  이 함수 하나가 "엑셀 워크북 → 위치 기반(iloc) DataFrame"을 만들고, **그 이후
  (`Preprocessor`, `TransformRegistry`, `OverrideApplier`, `CleanedSheetWriter`,
  `SummarySheetWriter`) 전부 이 DataFrame만 보고 동작한다** — 셀 객체나 워크북을 다시 참조하지
  않는다.
- 즉 사용자가 제안한 그대로: **"파일별로 DataFrame 만드는 로더 3개(xlsx/csv/json) + 이후는
  동일 로직"**이 정확한 목표 구조이고, ②·③ 단계는 **이미 그 모양대로 짜여 있어서 손댈 게
  없다.** 새로 짜야 하는 건 ①(로더)뿐이다.
- 진짜 엑셀 전용인 부분은 딱 두 곳뿐이고, 둘 다 국지적이다:
  1. `analyzer.py`의 헤더 행 탐지(`detect_header_row`) — 병합 셀·다중 타이틀 행처럼 사람이
     손으로 만든 xlsx의 "머리말이 몇 번째 줄인지 애매한" 문제를 점수 매겨 추정하는 로직이다.
     CSV/JSON은 애초에 이런 모호함이 구조적으로 없다(헤더는 사실상 항상 0번째 행/키 목록) —
     오히려 xlsx보다 **더 단순**하게 처리 가능.
  2. `pipeline.py:63` `_write_raw_sheet()` — 정제 결과 워크북에 "원본" 시트를 그대로 끼워
     넣어 대조해 보는 **부가 기능**. 데이터 정제 로직과 무관한 내보내기 UX 옵션이다.
- new-beginnings의 CSV/JSON 지원이 clearsurvey보다 "쉬워 보이는" 이유는 포맷이 달라서가 아니라
  **애초에 clean_value/transform에 해당하는 정제 단계 자체가 없기 때문**이다(§1-A "결과 데이터
  소스" 행 참조 — 클라이언트에서 파싱한 값을 그대로 미리보기로 보여줌). 포맷 지원 범위가 아니라
  **정제 유무**가 두 프로젝트의 실제 차이다.

### 1-C. 이식 가능성 평가 — **정정: 중간 규모 작업으로 충분**

원래 "방향 A(정식 편입, 공수 큼) vs 방향 B(로컬 프리뷰, 공수 작음)"로 나눴던 판단도 재검토가
필요하다. §1-B에서 확인했듯 ②·③ 단계가 이미 포맷 무관이므로, **방향 A가 처음 평가보다 훨씬
저렴하다.**

**CSV 지원 — 실제 작업 범위**
1. `engine/analyzer.py`에 `CsvAnalyzer` 신설: 헤더는 원칙적으로 0번째 행 고정(엑셀처럼 점수
   매겨 탐지할 필요가 거의 없음), `pandas.read_csv`로 바로 DataFrame 확보.
2. `pipeline.py`에 `_sheet_to_dataframe()`과 같은 시그니처를 내는 `_csv_to_dataframe()` 추가 —
   0-based 컬럼·원본 행번호 index라는 동일 계약만 지키면 `Preprocessor` 이후는 **한 줄도
   안 고쳐도 된다.**
3. 실무 함정은 포맷 파싱이 아니라 **인코딩**이다 — 국내 설문 툴(네이버폼 등)이 내보내는 CSV가
   EUC-KR/CP949인 경우가 많음. `chardet`/`cchardet`로 인코딩 자동 감지 후 `pandas.read_csv`에
   넘기는 처리가 필요(신규 의존성 검토 필요 — `agents.md` 구조 변경 전 확인 원칙에 따라 패키지
   추가는 사용자 확인 후 진행).
4. `main.py`의 `.xlsx` 하드 게이트(§1-A)를 확장자별 분기로 변경.
5. 테스트: `backend/tests/test_config_excel.py`에 대응하는 `test_config_csv.py` 신설 —
   특히 "같은 데이터를 xlsx로 넣었을 때와 csv로 넣었을 때 `_data.json` 결과가 동일한지"를
   비교하는 회귀 테스트가 §1-B의 구조 정정을 실제로 지켜준다.
6. `_write_raw_sheet`(엑셀 전용 원본 대조 시트)는 CSV 입력 시 단순 스킵하거나, "원본 CSV를
   그대로 텍스트로 첨부 시트에 붙이기" 정도로 축소 대응.

**JSON 지원**: 배열-of-객체 구조라면 CSV와 사실상 동일(②·③ 무변경, `pandas.read_json` +
`_json_to_dataframe()`). 중첩 객체 구조라면 flatten 규칙을 먼저 정해야 함 — 실사용 수요를
먼저 확인.

**규모 재평가**: 최초 문서는 이 항목을 "중간 규모"로 뒀는데, §1-B 정정을 반영하면 **CSV는
"중"에서 "소~중" 사이, 핵심 리스크는 파이프라인 리팩토링이 아니라 인코딩 처리**로 좁혀진다.

## 2. 테마 색상 "정확도" 문제 — 특히 토스 차트에 주황이 섞이는 현상

> 사용자 코멘트로 범위를 명확히 함: 350종을 다 노출해 달라는 요청이 아니라, **"토스 테마에서
> 차트를 그리면 다른 프로젝트(파랑/검정/연파랑 계열)와 달리 이 프로젝트는 주황계열이 섞여
> 나온다 — 메인/서브/강조1/강조2 같은 색상 슬롯 매핑 자체가 잘못된 게 아닌가"**라는 지적.
> 아래는 이 질문에 대한 직접적인 답이다.

### 2-A. primary(메인) 색상 자체는 정확하다

clearsurvey `frontend/src/theme/toss.css`의 `--primary: oklch(0.56 0.243 261.078)`를 sRGB로
역변환하면:

```
oklch(0.56 0.243 261.078) → rgb(0, 100, 255) → #0064FF
```

new-beginnings `design-catalog.json`의 `toss.chart_palette[0]` 값도 **`#0064FF`로 완전히 동일**하다
(공식 Toss 브랜드 블루). 두 프로젝트가 같은 `design_system_guides/toss.md`를 소스로 삼기 때문에
메인 색상 정의 자체는 애초에 갈라질 수 없다. **문제는 메인이 아니라 chart-2~5(서브/강조 슬롯)에
있다.**

### 2-B. 주황의 정체 — 확인된 사실

`frontend/src/theme/toss.css`의 차트 5슬롯을 hex로 역변환해 실측하면:

| 슬롯 | 변수 | 역변환 hex | 의미 |
|---|---|---|---|
| chart-1 | `oklch(0.56 0.243 261.078)` | `#0064FF` | 토스 메인 블루 |
| chart-2 | `oklch(0.642 0.164 153.234)` | `#02A85A` | 초록(success 계열) |
| **chart-3** | `oklch(0.765 0.175 62.574)` | **`#FF9501`** | **주황(warning 계열)** |
| chart-4 | `oklch(0.606 0.219 292.717)` | `#8B5CF6` | 보라 |
| chart-5 | `oklch(0.743 0.127 204.646)` | `#00C2D1` | 시안 |

그런데 **이 값들은 스크립트가 실수로 채워 넣은 필러 색이 아니다.** 같은 디렉터리의
`frontend/src/theme/overrides/toss.json`을 열어 보면 정확히 이 5색이 **사람이 직접 기록해 둔
값**으로 들어 있다:

```json
{
  "_": "브랜드 색: primary #0064FF, success #00A85A, warning #FF9500. 자동 도출은
        secondary(#191F28 본문 네이비)를 골라 도넛이 검게 나왔고 chart-5가 chart-1과
        같은 파랑이었다. 네이비를 빼고 보라·시안으로 색상을 벌렸다.",
  "chart": {
    "light": ["#0064FF", "#00A85A", "#FF9500", "#8B5CF6", "#00C2D1"]
  }
}
```

즉 **`theme_system_plan.md` 작업 당시 누군가(과거 세션)가 의도적으로 내린 결정**이고, 컴파일된
`toss.css`도 이 override 값과 소수점까지 정확히 일치한다(직접 재변환해 확인함). **버그가
아니라 "의도된 색상 큐레이션 판단"**이다 — 다만 아래 이유로 그 판단 자체가 사용자 감각과
어긋난다.

### 2-C. 왜 이 판단이 브랜드 정체성과 어긋나는가

override 코멘트가 스스로 밝히듯, 이 5색을 고른 기준은 **`theme_system_plan.md` §2-D 원칙 1
"구분 가능성 우선"**이었다 — 5조각 도넛에서 색이 서로 겹치지 않게 hue를 최대한 벌리는 것.
그 결과 토스의 **자체 브랜드 색이 아닌 두 색(보라 `#8B5CF6`, 시안 `#00C2D1`)까지 끌어왔고**,
"빨강(error)만 피하면 된다"는 §2-D 원칙 3("error 계열 회피")은 지켰지만 **주황(warning)은
회피 대상에 없어서 그대로 남았다.** 즉 "빨강만 아니면 된다"는 규칙의 빈틈이다.

반면 사용자가 본 다른 프로젝트(또는 실제 토스 제품)의 인상 — "파랑/검정/연파랑 계열" — 은
전혀 다른 원리로 설명된다. new-beginnings의 카탈로그(`design-catalog.json`)는 브랜드마다
**primary 색상의 10단계 스케일**(`50`~`900`, 토스 기준 `#E8F2FF`~`#001A47`)을 통째로 갖고 있다.
이 스케일을 쓰면 "파랑 하나의 명도만 바꿔가며" 연파랑→파랑→거의 검정에 가까운 네이비까지
**단색 그러데이션 차트**를 만들 수 있다 — 사용자가 본 "파랑/검정/연파랑"은 categorical(범주별
다른 색상) 팔레트가 아니라 이런 **모노톤 계열 팔레트**였을 가능성이 높다.

**여기서 진짜 구조적 차이가 나온다**: clearsurvey의 CSS 테마 시스템(`theme/*.css`)은
`--chart-1`~`--chart-5` **5개 개별 색만** 정의하고, primary의 단계별 스케일(50~900)은 **아예
토큰으로 존재하지 않는다.** 그래서 지금 clearsurvey는 "브랜드 하나의 명도 변주" 같은 모노톤
팔레트를 애초에 만들 수 없고, 오직 5개의 서로 다른 hue를 쓰는 categorical 팔레트만 가능하다 —
그 categorical 5색을 정할 때 "구분 가능성"을 우선하다 보니 주황·보라·시안 같은 비브랜드색이
섞여 들어간 것이다.

> 참고: `frontend/src/lib/dashboardConfig.ts` 등 clearsurvey `lib/` 쪽에는 new-beginnings의
> `lib/theme.ts`에 해당하는 "JSON 레지스트리 + 전체 토큰(primary 50~900, neutral, shadow,
> motion) 런타임 적용" 엔진이 없다 — clearsurvey의 테마 시스템은 처음부터 "빌드 타임에 구운
> CSS 클래스" 방식으로 설계됐다(`theme_system_plan.md` §4-B, 방식 ① 채택 근거).

### 2-D. 적용 완료 (2026-07-24) — 값을 손으로 고치지 않고 도출 로직 자체를 고쳤다

> [!NOTE]
> 처음엔 `overrides/toss.json`의 값 5개를 손으로 바꾸는 방식으로 적용했으나, 사용자가
> "임의로 값을 수정하지 말고 `docs/design/design_system_guides`의 원형을 받아서 변환로직
> (메인/서브/강조1/강조2 등)에 따라 대입하는 형식이어야 한다"고 정정 요청 → **override 파일이
> 아니라 `frontend/scripts/build-themes.mjs`의 자동 도출 함수(`draftPalette()`) 자체를
> 고치는 방식으로 다시 적용했다.**

**근본 원인 재확인**: `draftPalette()`는 가이드 md의 색상 선언에서 후보를 뽑아 차트 5색을
자동 도출하는 함수이고, override 파일이 없는 테마는 전부 이 함수 결과를 그대로 쓴다. 기존
우선순위는 `[primary-500, info-fg, success-fg, warning-fg, secondary-500, primary-300,
primary-700]` 순이었다 — **브랜드 고유 색(서브/강조 톤)보다 semantic 색(success/warning/info)을
먼저 후보에 넣는 순서**였다. 그래서 override가 없었다면 자동 도출조차 orange를 넣었을 것이고
(직접 계산해 확인함: `[#0064FF, #00A85A, #FF9500, #191F28, #4795FF]`), 과거 `toss.json`
override가 굳이 손으로 개입해야 했던 이유도 결국 이 우선순위 자체였다.

**적용한 수정** (`frontend/scripts/build-themes.mjs`): 후보 우선순위를 **브랜드 색상 스케일
우선**으로 재정렬했다 — 메인(`primary-500`) → 서브(`secondary-500`) → 강조1(`primary-300`,
밝은 톤) → 강조2(`primary-700`, 어두운 톤) → 중립(`neutral-700`) → (5개가 안 채워질 때만)
info → success → warning 순으로 보충. error(빨강)는 기존 원칙대로 계속 제외.

**결과**: `overrides/toss.json` 자체를 삭제해도(=수작업 개입 없이) 이 로직만으로 토스 라이트
차트가 정확히 `#0064FF #191F28 #4795FF #003EA8 #8B95A1`(메인 블루·세컨더리 네이비·연파랑·
진파랑·중립 그레이)로 도출됨을 직접 컴파일해 확인했다. 다크 모드도 `toss.dark.md`의 같은
역할 토큰에서 자동 도출된다(수작업 없음). **이는 원형(`toss.md`)에 실제 정의된 값만 쓰고,
어떤 자유 hex도 새로 만들어 넣지 않은 결과다** — 사용자가 요구한 "원형 → 변환로직 → 대입"
형식을 그대로 만족한다.

**영향 범위 확인**: 활성 15종 중 override 파일이 없던 테마는 `datadog`뿐이었고(나머지는
기존 override가 여전히 우선 적용되어 무영향), 우선순위 변경으로 `datadog`의 차트도 자동
재도출됐다(보라 메인 + 브랜드 세컨더리 코랄 + 밝은/어두운 보라 + 중립 그레이 — 여전히 브랜드
색 범위 안). `bunx vitest run src/theme/__tests__/theme.test.ts`(테마 무결성 135개)와 전체
프론트 테스트(481개) 모두 통과 확인. 변경 파일: `build-themes.mjs`(로직),
`overrides/toss.json`(삭제), 재생성된 `toss.css`/`datadog.css`/`presets.css`/`catalog.json`.

**남은 확인 사항**: 이 문서 작업은 코드/데이터 레벨 검증까지만 했다 — 실제 대시보드 화면에서
5조각 이상 도넛 차트를 띄워 색이 시각적으로 잘 구분되는지(특히 근흑색 네이비 조각이 "구멍"
처럼 보이지 않는지)는 아직 육안 확인 전이다. 배포 전 브라우저에서 확인 권장.

**구조 확장 (별도 검토, 이번 적용 범위 아님)**: primary 50~900 색상 스케일을 테마 토큰에 추가해
모노톤 그러데이션 팔레트까지 지원하려면 `theme/tokens.ts`에 `--color-primary-{50..900}` 토큰
추가, 15종 CSS 전체에 값 채우기, 차트 컴포넌트에 "categorical vs sequential" 선택 로직 추가가
필요하다 — new-beginnings의 `lib/theme.ts` 토큰 체계를 참고해 이식 가능하나 규모가 크므로 별도
계획으로 분리한다.

**참고 — 테마 가짓수(15종)는 이번 지적과 무관**: 사용자가 명확히 한 대로 "350종을 다 꺼내
달라"는 요청이 아니었으므로, 활성 테마 수 확대는 이 문서의 우선순위에서 제외했다(필요하면 별도
논의).

## 3. 균형 잡힌 시각 — clearsurvey가 실제로 앞서는 지점

사용자 요청이 격차 분석이므로 clearsurvey의 열세만 부각되기 쉽지만, 구조적으로 우위인 부분도
있다는 걸 함께 기록해 둔다(향후 "그냥 new-beginnings 방식으로 갈아타자"는 판단을 막기 위함):

- **데이터 정합성**: NaN 방어·transform 검증·overrides.json 수기 교정·git sync·421개 백엔드
  테스트 — new-beginnings의 클라이언트 프리뷰 경로에는 대응물이 없다.
- **PDF/PPT 내보내기의 색상 정확도**: oklch/color-mix 문제를 실측 근거로 해결(`pdfColorFix.ts`)한
  상태이며, 이는 오히려 clearsurvey 쪽이 new-beginnings보다 앞서 있을 가능성이 높은 지점이다
  (new-beginnings 쪽 내보내기 색상 처리는 이번 조사에서 확인하지 못함 — 필요시 별도 확인).
- **차트 팔레트의 "검수됨" ≠ "브랜드 충실도"**: §2-B·2-C에서 확인했듯 clearsurvey 활성 15종은
  기계 합성이 아니라 사람이 손으로 확정한 값이지만, 그 판단 기준이 "구분 가능성 우선"이라
  브랜드 정체성과 어긋날 수 있다(토스의 주황이 그 사례). 반대로 new-beginnings는 브랜드
  faithful한 10단계 primary 스케일을 갖고 있지만, categorical 차트 색은 기계 합성
  (`synthesizePalette()`)이라 error(빨강)까지 섞여 들어갈 수 있다(§0 표). **"검수 여부"와
  "브랜드 충실도"는 서로 다른 축이며, 둘 다 완벽하지 않다.**

### 4-A. 활성 테마 재점검 결과 — 10개 전부 유지, 알고리즘 수정은 toss/datadog에만 적용됨

`build-themes.mjs`의 `draftPalette()` 우선순위 변경(§2-D) 후, override가 있던 나머지 9개
가이드 기반 테마(airbnb·anthropic·apple-hig·claude·duolingo·github-primer·kakao·linear·vercel)
+ 수작업 테마 ink를 새 알고리즘 결과와 대조했다. **10개 전부 override를 그대로 유지하기로
결정** — 토스와 달리 이유가 다르다:

| 테마 | 새 알고리즘이 못 고치는 문제 | 결론 |
|---|---|---|
| airbnb, anthropic, apple-hig, claude, duolingo, github-primer, kakao, vercel | primary 램프(300/500/700)가 서로 색상만 다르고 같은 색상군이라, 5색 중 3개가 뭉친다(예: kakao는 새 알고리즘도 `#FEE500`·`#FEE52B` 두 슬롯이 거의 같은 노랑) | override 유지 — 브랜드 고유 다색 정체성(애플 시스템 컬러, 듀오링고 캐릭터 색, 깃허브 실제 그래프 색 등)이 알고리즘보다 낫다 |
| linear | 새 알고리즘이 secondary(`#EB5757`, 빨강 기미)를 2번 슬롯으로 끌어올림 — 기존 override가 의도적으로 피했던 색이 되살아남 | override 유지 — **새 알고리즘의 알려진 한계**(토큰 출처와 무관하게 red-ish hue를 걸러내는 로직이 없음)를 확인 |
| ink | 가이드가 없는 수작업 테마라 애초에 draftPalette() 대상이 아님 | 무관, override 유지 |

**부수 발견**: 알고리즘 변경으로 override가 없던 `datadog`도 함께 재도출됐다(보라 메인 + 브랜드
세컨더리 코랄 + 명암 변주 + 중립 그레이). datadog의 secondary(`#FF7B72`)도 linear와 같은
"코랄/빨강 기미" 특성이 있으나, datadog 자신의 실제 브랜드 색이라 override로 굳이 덮지 않고
그대로 뒀다 — 다만 이후 육안 확인 시 함께 살펴볼 것을 권한다(§5 남은 확인 사항).

### 4-B. CSV/JSON 업로드 지원 — §1-C 예상대로 파이프라인 리팩터링 없이 완료

§1-B에서 확인한 대로 `_sheet_to_dataframe()` 계약만 지키면 이후 로직이 전부 포맷 무관이라는
사실이 실제로 들어맞았다.

- **분석기 계층 분리**: `generate_config_yaml`/`generate_draft_xlsx`(포맷 무관)를
  `engine/base_analyzer.py`의 `BaseAnalyzer`로 추출. `ExcelAnalyzer`(analyzer.py)는 병합 셀
  기반 헤더 탐지만 남기고, `CsvAnalyzer`(csv_analyzer.py)·`JsonAnalyzer`(json_analyzer.py)를
  신설해 `sheet_names()`/`detect_header_row()`/`all_headers()` 세 메서드만 구현.
- **CSV**: `pipeline.py`에 `_csv_to_dataframe()` 추가. 인코딩은 외부 의존성 없이
  `utf-8-sig → utf-8 → cp949 → euc-kr` 순서로 자동 감지(국내 설문 툴의 CP949 내보내기 대응).
  값 보정(`_coerce_csv_value`)에서 **앞자리 0이 있는 숫자열(전화번호 등)은 정수로 바꾸지
  않는 정규식**을 넣어, "01012345678"이 1012345678로 깨지는 사고를 방지.
- **JSON**: 평면 배열-of-객체(`[{...}, ...]`)만 지원(`json_analyzer.py`). 중첩 구조는 flatten
  규칙이 제품 결정 사항이라 범위 밖으로 명시적으로 남기고, 명확한 `JsonFormatError`로 거부한다.
  키가 레코드마다 달라도 첫 등장 순서 기준 합집합을 헤더로 삼아 위치 기반 나머지 파이프라인과
  계약을 맞춘다.
- **main.py**: `.xlsx` 하드 게이트를 `_ANALYZER_BY_EXT` 딕셔너리 기반 분기로 교체. 이 김에
  **잠재 버그도 함께 정리**했다 — 프론트는 `.xls`를 허용한다고 표시했지만 서버는 애초에
  `.xlsx`만 받았고, `.xls`(레거시 바이너리)는 openpyxl이 읽지도 못한다. `.xls` 표기를 양쪽에서
  제거했다(작동한 적 없는 기능을 "지원"이라 표시하지 않는다).
- **검증**: xlsx/csv/json 세 포맷에 **동일 데이터**를 넣어 Cleaned 시트 결과가 바이트 단위로
  같은지 비교하는 회귀 테스트(`test_config_csv.py`, `test_config_json.py`) 포함, 신규 29개
  테스트 전부 통과. 백엔드 전체 스위트 421→**466개**, 프론트 전체 481개 통과.

### 4-C. primary 50~900 스케일 — 범위를 의도적으로 축소했다

원안은 "차트 컴포넌트에 categorical/sequential 팔레트 선택 로직까지" 였으나, 이는 **어떤
차트가 모노톤을 쓸지, 사용자가 고를 수 있게 할지 같은 제품 결정을 AI가 임의로 정하는 것**이라
`agents.md` §6("임의 기능 추가 금지 — 목업에 없는 설정창을 욱여넣지 않는다")에 저촉된다고
판단해 **데이터 계층까지만** 구현했다:

- `build-themes.mjs`가 각 가이드의 `--color-primary-50`~`900`(원래도 파싱은 됐으나 버려지던
  값)을 추출해 CSS 커스텀 프로퍼티로 함께 컴파일하도록 수정(`extractPrimaryScale()`).
- 가이드가 있는 활성 11종(토스 등)에만 스케일이 생기고, 가이드가 없는 4종(`light`/`dark`/
  `ink`/`forest`)은 억지로 채우지 않음 — `theme/tokens.ts`에 `PRIMARY_SCALE_STEPS`를
  **선택적** 필드로 명시(기존 `COLOR_TOKENS`처럼 전 테마 필수로 만들지 않음).
- 컴포넌트(`ChartCard.tsx` 등)를 이 토큰을 쓰도록 바꾸는 작업은 **하지 않았다** — 이건 후속
  제품 논의 대상으로 남겨둔다.
- 테스트: 11종 전부 10단계가 빠짐없이 있는지, 드롭인 CSS와 카탈로그 값이 일치하는지,
  "50번이 900번보다 밝다"(끝점 불변식 — vercel처럼 500에서 바닥을 찍고 600~900이 다크모드
  표면색으로 다시 밝아지는 정당한 예외가 있어 완전한 단조 감소는 강제하지 않음) 검증.
  프론트 전체 스위트 481→**505개** 통과.

### 4-D. 리커트 척도(1~5 등) 오분류 수정 — CSV/JSON 작업의 부작용 대응

CSV/JSON 업로드는 엑셀의 "텍스트 서식" 같은 회피 수단이 없어, 설문 응답이 정수(1~5, 0~10 등)로
저장되면 `_detect_type()`이 무조건 `numeric`으로 분류하고 `_build_default_dashboard()`가 첫
numeric 컬럼으로 "OO 합계" KPI를 자동 제안하는 기존 문제가 CSV/JSON에서 더 잘 드러나게 됐다
(xlsx도 셀이 진짜 숫자면 동일 문제가 있었으나, "텍스트 서식"으로 우회 가능했다).

`backend/engine/exporter.py`에 `_looks_like_rating_scale()`을 추가해 `_detect_type()`이 아래
조건을 모두 만족하면 `numeric` 대신 `category`로 분류하도록 수정:

1. 값이 전부 정수(소수 섞이면 실측 평균일 수 있어 제외)
2. 0 또는 1에서 시작하고 최댓값이 10 이하(리커트 1~5·1~7, NPS 0~10 범위)
3. 고유값 3~11개(2개=이진 플래그는 제외 — `_build_default_dashboard`의 O_ 접두사 multibar
   자동 구성이 그 컬럼을 `numeric`으로 계속 인식해야 하므로 건드리지 않음), 응답 수가 고유값의
   최소 2배(반복 응답이 있어야 "척도"로 봄 — `[1,2,3,4,5]` 같은 단순 나열은 그대로 numeric)

`_build_default_dashboard` 자체는 안 고쳤다 — `type`만 정확해지면 기존 로직이 알아서 도넛
차트를 만든다. 신규 테스트 10개(리커트/NPS/이진플래그/연도/소수점 평균/과다 고유값 등 경계
케이스 + end-to-end 1개) 추가, 뮤테이션 테스트로 실제로 무는지 확인. 백엔드 스위트
466→**476개** 통과.

**주의(육안 확인 필요)**: `_build_default_dashboard`가 만드는 건 **최초 자동 제안**일 뿐이다.
이미 만들어진 기존 프로젝트의 `dashboard.json`에는 소급 적용되지 않는다 — 기존에 잘못된
"OO 합계" KPI가 있는 프로젝트는 Step2에서 수동으로 걷어내거나 프로젝트를 재분석해야 한다.

## 5. 남은 확인 사항

- **육안 확인 미완료**: 새 toss/datadog 차트 팔레트가 실제 도넛/바 차트에서 잘 구분되는지
  브라우저로 확인 안 함. 특히 toss의 `#191F28`(근흑색 네이비)이 화면에서 "구멍"처럼 보이지
  않는지, datadog의 코랄(`#FF7B72`)이 위험색으로 오독되지 않는지 확인 필요.
- **primary 스케일의 실제 소비처 없음**: §4-C에서 의도적으로 컴포넌트 연동을 하지 않았으므로,
  지금 이 스케일은 CSS에 존재만 하고 어디서도 읽지 않는다. 모노톤 팔레트가 실제로 필요한
  화면(예: 순서형 5점 척도 분포 차트)이 나오면 그때 컴포넌트 쪽을 논의한다.
- **기존 프로젝트 소급 미적용**: §4-D의 리커트 재분류는 새로 만드는 프로젝트(또는 재분석)에만
  적용된다. 이미 배포된 프로젝트 중 리커트 컬럼이 "합계" KPI로 잘못 나오고 있는 게 있는지
  확인이 필요하면 실제 프로젝트 목록을 점검해야 한다.
- **커밋 안 함**: 이번 대화의 모든 변경은 워킹트리에만 있다. 사용자 확인 후 커밋 필요.

이 문서는 §0~§3(분석)과 §4~§5(실행)를 모두 포함해 **완료 상태**다. 후속 후속작업(육안 확인,
primary 스케일 실제 적용)이 필요해지면 새 계획서로 분리해 `docs/plan/pending/`에 둔다.

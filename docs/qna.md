### 2. 설정편집 — 불러오기/저장/미리보기

**기준 파일**: 실제 저장소는 `storage/projects/{project}/config.yaml` + `dashboard.json` 두 개. 백엔드 `GET/POST /api/projects/{name}/config` (`backend/app/main.py:686`, `:731`)가 이 두 파일을 읽고 쓴다. `config.yaml`은 `SurveyConfig.model_validate`로 Pydantic 검증까지 거친다.

**"config.json 형식 아님" 오류 — 포맷 불일치이지 버그 아님.** `Step2_ConfigEditor.tsx:194-201`은 오직
```js
const parsed = JSON.parse(text);
if (parsed.config && parsed.dashboard !== undefined) { ... }
else { alert("유효한 ClearSurvey 설정 파일이 아닙니다."); }
```
`{ config: {...}, dashboard: {...} }` 래핑 형태만 받는다. 이건 같은 화면의 "파일로 저장"(`handleSaveToFile`, 166-182줄)이 만드는 **백업 전용 포맷**이다. 실제 저장 포맷은 이것과 다른 `config.yaml`(YAML, unwrapped)이므로, 다른 프로젝트의 config.yaml이나 손으로 만든 json은 전부 거부된다. → "이 화면에서 내보낸 백업 json만 다시 불러올 수 있다"가 현재 사양.

**"설정 불러오기"(Step2) vs "기존 설정 복사하기"(Step1) — 정확한 구분.** 두 기능 모두 "설정을 재사용한다"는 목적은 같지만, **적용 대상 프로젝트가 지금 막 새로 만드는 것이냐, 이미 존재하는 것이냐**로 완전히 나뉜다. 둘 중 하나로 대체 가능한 관계가 아니라, 애초에 쓸 수 있는 시점 자체가 겹치지 않는다.

| 구분 | 기존 설정 복사하기 (Step1) | 설정 불러오기 (Step2) |
|---|---|---|
| **쓸 수 있는 시점** | 새 프로젝트를 만드는 그 순간뿐 (엑셀 업로드와 동시에) | 이미 만들어진 프로젝트를 편집할 때 언제든 |
| **소스 설정의 위치** | 지금 이 인스턴스(`storage/projects/`)에 살아있는 프로젝트만 드롭다운에 뜸 | 로컬 PC에 저장된 백업 파일(`*_config_backup.json`) — 어디서 받았든 무관 |
| **필요한 사전 작업** | 없음 (드롭다운에서 고르기만 하면 됨) | 소스 프로젝트에서 미리 "파일로 저장"을 눌러 백업 json을 받아둬야 함 |
| **적용 방식** | 서버가 config.yaml을 새 프로젝트로 즉시 복사 (원클릭, 자동 저장까지 완료) | 브라우저가 파일을 읽어 화면 상태만 바꿈 → 하단 저장 버튼을 눌러야 디스크에 반영 |

**따라서 실무 판단 기준은 하나뿐이다: "지금 새 프로젝트를 만드는 중인가?"**
- **그렇다** (Step1에서 엑셀을 막 올리는 중이고, 원본 설정 프로젝트가 지금 이 화면 드롭다운에 보인다) → **"기존 설정 복사하기"**를 쓴다. 이게 유일하고 가장 쉬운 방법이며, 별도 파일 다운로드/업로드 없이 한 번에 끝난다.
- **아니다** (프로젝트가 이미 만들어져 있고, 나중에 다른 설정을 덮어씌우고 싶다) → Step1로 되돌아갈 수 없으므로 **"설정 불러오기"**가 유일한 방법이다. 이 경우 반드시 ① 소스 프로젝트의 Step2에서 "파일로 저장" → ② 대상 프로젝트의 Step2에서 "설정 불러오기"로 그 파일 선택 → ③ 확인창 승인 → **④ 하단 저장 버튼(미리보기/저장 후 대시보드/저장 후 파이프라인 중 아무거나)을 눌러야 실제로 저장됨** — ④를 잊으면 화면만 바뀌어 보이고 새로고침하면 사라진다. (다른 PC에서 만든 프로젝트의 설정을 가져오는 경우도 이 경로다 — `storage/`는 PC 간 동기화되지 않으므로, 파일로 내보내 옮기는 것 외에 다른 방법이 없다.)

즉 7번 항목("데이터만 교체")의 정공법은 **항상 "기존 설정 복사하기"** — 새 프로젝트를 만들면서 데이터를 교체하는 시나리오이기 때문이다. "설정 불러오기"는 이미 존재하는 프로젝트에 뒤늦게 다른 설정을 적용하는, 별개의 보조 경로로 이해해야 한다.

### 3. KPI 카드 — 유사명칭/조건조합

✅ **와일드카드 문법이 이미 구현되어 있음(단, 안내가 없어 안 보임).** `frontend/src/components/dashboard/KpiRow.tsx:19-49`:

- `창비*` / `*창비` → 시작/끝
- `<>창비` 또는 `!=창비` (및 `<>*창비*`) → 제외
- 접두/접미 기호 없이 값만 입력 → **정확히 일치**(exact)가 기본값

즉 "창비"만 입력하면 정확일치라서 "창비출판사"를 못 잡는다 — `*창비*`라고 써야 하는데, 설정 UI(`ChartConfigCard.tsx:93-99`, 값 입력창)에 이 문법에 대한 힌트가 전혀 없다.
→ **즉시 가능한 개선**: 입력창 placeholder/도움말에 `*값*`=포함, `<>값`=제외 문법 안내 추가 (코드 로직 변경 없이 UX만 개선).

❌ **OR 조합("창비 or 문학")은 미지원.** 카드 하나의 `value`는 단일 패턴만 표현 가능해서 여러 카드로 우회하는 수밖에 없다.
→ **구현 방향**: `value`를 `,` 구분 다중 패턴 또는 배열로 확장하고 매칭 로직에 OR 결합 추가.

### 4. 에러 — `cannot access local variable 'math'`

🐛 **수정 완료.** 원인은 `backend/transforms/domain/cleansing.py`의 `normalize_number()` 함수 내부에 있던 중복 `import math` (구 143번째 줄). 파이썬은 함수 안 어디에 `import math`가 있으면 그 순간부터 함수 **전체 스코프**에서 `math`를 지역 변수로 취급한다. 그런데 그 지역 import 문이 실행되기도 전인 115번째 줄에서 이미 `math.isnan(val)`을 참조하고 있어서(숫자 컬럼에 빈 셀/NaN이 있을 때), `UnboundLocalError: cannot access local variable 'math'`가 발생했다. 모듈 최상단(25번째 줄)에 이미 `import math`가 있으므로 함수 내부의 중복 import를 삭제해서 해결. `gpu_4` 사례처럼 정제 대상 숫자 컬럼에 결측치가 하나라도 있으면 100% 재현되던 버그였다.

- 수정 파일: `backend/transforms/domain/cleansing.py`
- 검증: `pytest -q` 백엔드 전체 421개 테스트 통과 확인, `normalize_number(float('nan'))` 수동 재현 테스트로 정상 동작(→ `None`) 확인.

Radix Tabs는 비활성 탭의 콘텐츠를 DOM에서 제거하므로, 목록검색 탭에서는 `chartGridRef.current`가 `null`이 되어 `if (!chartGridRef.current || !data) return;`에서 **에러 토스트도 없이 조용히 무동작**한다. 반대로 PPT(`handleExportPptx`, 88-99줄)는 DOM 캡처가 아니라 `cfg`/`filtered`/`data` 같은 순수 데이터로 pptx를 직접 생성하므로 탭과 무관하게 동작한다.

### 6. 원본엑셀 (clean xlsx) 다운로드

> **2026-07-22 업데이트**: 스크린샷 두 장(`Snipaste_2026-07-22_11-09-20.png`, `-48.png`)으로 실제 재현된 books 프로젝트의 "복구" 경고를 근거로 Excel COM 자동화(PowerShell)를 이용해 실제 파일을 직접 열고-저장하며 원인을 이진 탐색으로 특정했다. 아래는 그 결과다.

**a) summary 시트 비율표시 오류 — $B$3 고정** — 🐛✅ **수정 완료.** `backend/engine/summarizer.py`의 `total_cell` 계산 로직이 "totals" 타입 섹션 + layout(그리드) 설정이 **모두** 있을 때만 실제 위치를 계산하고, 그 외(= `unique_count`/`binary_sum`/`countif_contains`만 쓰는 대부분의 프로젝트, books/gpu_4 포함)에는 무조건 `"$B$3"` 리터럴로 폴백해서, 실제 합계가 B3에 없으면 모든 비율 수식이 엉뚱한 값을 나눴다.
→ **적용한 수정**: `totals` 섹션도 없고 `summary.total_cell`을 config에 명시하지도 않은 경우, `"$B$3"` 대신 정제 시트의 실제 데이터 행수를 그 자리에서 세는 `COUNTA('Cleaned'!A3:A10000)` 형태의 수식으로 대체했다. 어떤 섹션 구성이든 항상 올바른 분모를 쓰게 된다. 회귀 테스트(`test_summarizer_total_cell_fallback_avoids_wrong_b3`) 추가, 백엔드 424개 테스트 전부 통과 확인.

**b) 다운로드 시 경고문구 & d) summary 시트 수식 문제 — 🐛✅ 핵심 원인 확정 및 수정 완료.** 실제로는 **하나의 근본 원인**이었다: Excel은 함수 종류와 무관하게 **수식에 직접 박아 넣는 문자열 리터럴이 255자를 넘으면 그 수식 전체를 무효 처리하고, 파일을 열 때 "복구" 대화상자와 함께 통째로 제거**한다(COUNTIF 전용 제약이 아니라 Excel 수식 엔진 자체의 일반 제약 — Excel COM으로 합성 테스트해 정확히 확인: 255자는 정상, 256자부터 손상 재현됨).

books 프로젝트의 "저자" 컬럼처럼 한 셀에 공동저자 수십 명이 쉼표로 나열된 값이 있으면, `unique_count` 요약 섹션이 그 값을 통째로 하나의 "고유값"으로 취급해 `=COUNTIF('Cleaned'!D3:D10000,"신경림, 강성은, ... 71명 나열 ; 298자")` 같은 수식을 만든다 — 정확히 이 한 줄(실측: 전체 22,136개 수식 중 정확히 이 행)이 파일 전체를 손상시키고 있었다. Excel COM으로 실제 파일을 열고-복구하는 과정을 자동화해 이진 탐색(8674행 → ... → 정확히 4060행)으로 범인 수식을 특정했다.
→ **적용한 수정** (`summarizer.py`, `unique_count`/`countif_exact` 섹션): 값을 수식에 리터럴로 재삽입하는 대신, 이미 같은 행의 라벨 셀에 그 값이 그대로 쓰여 있으므로 **그 셀을 참조**하도록 변경 — `=SUMPRODUCT(--('Cleaned'!D3:D10000=F4060))` 형태. 셀 참조는 문자열 길이 제한이 전혀 없어 원천적으로 안전하다. 회귀 테스트(`test_summarizer_long_value_avoids_255_char_formula_literal`) 추가, books 프로젝트로 파이프라인을 실제로 재실행해 이 수식 자체는 더 이상 파일을 손상시키지 않음을 확인.

`storage/projects/books/output/books_cleaned.xlsx`는 이번 세션 중 실제로 재생성해 위 수정들을 검증했다 — 지금 디스크에 있는 파일은 슬라이서를 뺀 상태(`include_slicers: false`)로 만들어졌고 Excel COM 재현 테스트를 통과했다(경고 없이 열림). **다만 이건 검증용으로 임시로 끈 것**이라 books 프로젝트의 실제 저장된 설정(config.yaml/json)에는 반영되지 않았다 — 화면에서 다시 파이프라인을 돌리면 슬라이서가 기본값(켜짐)으로 재생성되어 손상이 재현된다. 위에서 추가한 "슬라이서 포함" 체크박스를 꺼서 저장한 뒤 다시 실행해야 계속 깨끗한 상태로 유지된다.
